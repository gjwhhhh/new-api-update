# 容器版本更新规则

本文件约束服务器版本更新，以及发布脚本的实现、修改和评审。相关任务必须在规划和执行前完整阅读本文件，并遵守 `AGENTS.md` 的部署与镜像构建要求。用户已经授权的版本更新应连续完成准备、替换、恢复和验证，不重复索取例行确认。

## 更新方式与目标

- 默认直接更新现有 Docker Compose 项目的指定应用服务，保留原有端口、数据挂载、环境配置和代理入口。未经用户要求，不另建并行应用实例，不改用蓝绿发布。
- 所有镜像必须在远端 CI 构建并发布。服务器只拉取、替换和运行已发布镜像，禁止 `docker build` 或任何源码编译构建。
- 单容器替换允许存在退出、创建、启动和必要迁移带来的短暂中断。必须将下载、备份、配置排查等准备工作移出停机窗口，避免容器停在 `Created` 而无人继续启动。
- 更新只作用于指定应用服务，不顺带更新、重启数据库、Redis、代理或其他应用，不执行 `compose down`、卷删除或镜像清理。

## 第一阶段：旧版本运行期间完成准备

以下准备全部完成后才能替换旧容器；任何一步失败，保留旧服务和原部署配置，报告具体失败原因。

1. **确认操作目标。** 核对 SSH 主机、Compose 项目名、工作目录、配置文件、环境文件、服务名、端口、挂载和当前镜像摘要。验证 Docker、Compose、非交互权限及所需命令可用，记录当前服务健康状态和对外版本。
2. **确认发布产物。** 核对对应 CI 已成功，明确本次目标提交、镜像版本、摘要和 CPU 架构。将已核实的不可变摘要用于部署，不仅依赖会移动的 `latest` 或 `custom-prod` 标签。
3. **提前拉取镜像。** 在旧容器运行期间，通过 Compose 拉取目标应用镜像，确认本机实际镜像摘要和架构正确。保留旧镜像并确认其可用于恢复，禁止在替换时再等待下载。
4. **备份并验证。** 备份 Compose 配置、环境文件及受本次更新影响的数据；数据库使用适合当前引擎的一致性备份。流水线启用 `pipefail`，核对退出码、备份文件及压缩完整性。备份限制访问权限，不输出凭据或业务数据到聊天和公开日志。
5. **校验候选配置。** 在独立候选文件中准备新镜像配置，保持原项目名、目录和环境文件解析方式；候选文件位置变化不得导致生成另一个 Compose 项目或改变相对挂载路径。使用 `compose config` 校验，并只输出必要的非敏感结果。
6. **检查迁移和恢复条件。** 确认数据库变更、预计启动时间、旧版能否读取升级后的数据库，以及镜像回退边界。回退不兼容且用户未授权必要维护范围时，必须在停止旧容器前说明阻碍，不能在停机后再决定处理方式。
7. **检查资源和执行任务。** 确认磁盘、内存、依赖服务及代理正常；备好完整发布脚本、旧配置、旧镜像、阶段日志、超时和恢复入口。准备失败不得修改在线服务。

## 第二阶段：服务器端连续执行替换

- 发布必须交给服务器端 systemd 服务/临时服务，或具备同等进程监管能力的机制执行。任务不能依赖聊天工具进程、SSH 连接或交互终端存活；仅使用长 SSH 命令、`nohup` 或 `set -e` 不满足要求。
- 服务器端任务必须持有当前 Compose 项目的独占部署锁，避免重复发布或恢复任务同时操作同一服务。启动任务后应取得可再次查询的任务标识，记录日志和最终退出状态；本地等待结束不等于服务器端发布完成。
- 在停机前再次确认准备已完成、候选版本正确，原子替换部署配置。使用现有项目的 `docker compose up` 更新指定应用服务；采用 `--no-deps`、`--no-build`、`--pull never`，禁止引入临时下载或构建。
- 不先单独执行 `stop`、`down` 或 `create` 再等待下一轮交互。启动与健康等待属于同一次服务器端执行，Compose 版本支持时使用 `--wait` 和明确的 `--wait-timeout`，并继续完成公网验证。
- 不在容器替换中途暂停等待用户例行确认。客户端断开后，服务器端任务必须继续完成启动、验证或恢复；重新连接时先查询原任务，不能盲目再发起一次更新。
- 切换、启动等待、重试和恢复都必须设置有限超时和次数。超时预算应覆盖现有 `stop_grace_period`、应用优雅退出时间、必要迁移及健康检查间隔，不能将正常退出等待误判为故障。
- 不为缩短中断而擅自压缩 SSE、WebSocket 或其他长请求的优雅退出时间；如需调整，先明确业务影响并完成对应验证。

## 异常恢复：禁止留下未启动的容器

进入替换阶段后，命令返回错误、超时或部署任务异常退出，都必须触发服务器端恢复流程。该流程必须有阶段记录和独立监管/失败处理入口，不能仅依赖可能随进程一起消失的 shell `EXIT` trap。

1. **先确认真实状态。** 核对任务是否仍在执行、部署锁、容器所属项目/服务、目标镜像和健康状态，再决定恢复动作。不能因为 SSH 断开就认定部署已失败，也不能与仍在运行的 Compose 命令并发恢复。
2. **目标容器停在 `Created`。** 在任务确认退出且可以独占恢复后，立即通过同一项目的 `compose up` 启动指定服务，并等待健康检查，不停在“已经创建”的结果上。默认最多补启动一次；若仍失败，进入镜像回退判断。
3. **目标容器退出或持续不健康。** 记录退出码、OOM 状态及经过脱敏的启动/迁移错误，执行预先定义的有界恢复。不得无限重启、临时删库、重建卷或在服务器编译修复。
4. **镜像回退。** 仅在第一阶段已确认迁移兼容时，恢复旧 Compose 配置与旧镜像，通过 `compose up` 启动，并重新检查本机和公网服务。回退成功必须报告“更新失败、旧版已恢复”，不能报告更新成功。
5. **无法自动恢复。** 如果迁移已改变兼容性或恢复失败，立即说明当前服务状态、失败原因、任务日志及下一步所需操作。不得自动恢复数据库备份覆盖更新后产生的线上数据。

进程监管必须覆盖“任务退出时容器仍未启动”的情况。脚本中写了恢复分支，不代表任务被终止后该分支一定会执行；必须验证监管机制确实能够接续恢复。

## 完成验证与交付

以下条件全部满足，才可以报告本次更新完成：

- 容器属于预期 Compose 项目和服务，实际运行镜像与目标摘要一致，处于运行且健康状态；不能只检查 `compose up -d` 的退出码。
- 本机状态接口返回预期新版本，启动和迁移完成，没有阻碍运行的启动错误或反复重启。
- 通过实际公网域名检查状态接口和必要页面，核对版本，确认代理链路正常；不能只用容器内接口代替公网验证。
- 确认数据库、Redis 和其他非目标服务没有因本次更新被额外重建或重启。
- 保存目标主机、任务标识、旧/新版本与摘要、备份位置、准备/替换/恢复各阶段时间、验证结果及最终状态。时间明确时区；中断时长以实际探测为准，仅有部分日志时报告已观察到的失败窗口，不能冒充完整中断时长。

交付必须区分“新版更新成功”“更新失败但旧版已恢复”“仍未恢复”。若任务仍在执行，应继续查询和处理，不能提前结束为成功，也不能将剩余启动动作留给用户发现后补做。

## 发布机制的验收要求

首次实现或修改发布脚本及其监管机制时，在隔离环境验证下列场景；不得为了演练而中断生产服务：

| 场景 | 必须满足的结果 |
| --- | --- |
| 正常更新 | 指定服务运行目标版本，本机、公网和健康验证全部通过 |
| 拉取、备份或配置校验失败 | 不进入替换阶段，旧服务和原部署配置保留 |
| SSH/本地等待进程中断 | 服务器端任务继续，重新连接可查询同一任务和最终结果 |
| 目标容器停在 `Created`，发布执行进程退出 | 监管机制触发恢复，有界补启动并验证，不留下无服务状态而无处理 |
| 新版本启动失败 | 按迁移兼容性执行回退或明确报错，不无限重启、不覆盖数据库 |
| 重复发起更新 | 部署锁阻止并发替换，不产生两个相互竞争的发布任务 |

本文件定义后续更新必须遵守的行为，不代表服务器端脚本和监管机制已经实现或通过演练。文档修改不能作为发布机制验收通过的证据；未具备这些执行保障时，应先完成准备，不能继续使用已知会留下半完成状态的方式替换线上容器。
