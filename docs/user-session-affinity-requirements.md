# 用户级关闭会话保持需求文档

版本：v0.4（包含实现、评审修复与验证记录）

日期：2026-10-16

状态：功能已实现，针对性验证通过；扩大回归的未通过项见第 11 节

## 1. 需求目标

在保留当前全局会话保持能力的基础上，允许管理员针对指定用户关闭会话保持，其他用户继续执行原有策略。

例如：系统对大部分用户开启严格会话保持，但用户 A 希望每次请求重新参与正常渠道调度。管理员只需关闭用户 A 的会话保持，无需修改全局规则，也不影响用户 B。

这里的“会话保持”指网关根据会话标识复用已绑定的上游渠道，不涉及网页登录状态或登录有效期。

## 2. 当前能力与缺口

根据当前项目代码，已有能力包括：

- 全局开启、关闭会话保持，并配置默认会话行为。
- 按模型、请求路径、客户端特征和会话标识匹配规则。
- 每条规则可继承全局行为，或单独配置关闭、优先保持、严格保持。
- 会话绑定具有有效期，可配置切换成功后更新绑定、渠道不可用时是否保留绑定。
- 用户已有独立的渠道优先级配置；会话绑定在渠道自动排序之前生效。
- 会话规则还可以附带请求参数覆盖、请求头透传等配置。

目前缺少“指定用户始终不参与会话绑定”的用户级配置。

## 3. 本期范围与默认假设

按本次实施范围采用以下口径：

已明确的入口要求：保留用户管理入口，并在“会话与重试”设置中增加用户配置区。

| 项目 | 建议范围 |
| --- | --- |
| 配置主体 | 用户账号，以用户 ID 为准 |
| 操作角色 | 拥有相应路由管理权限的管理员 |
| 管理入口 | 用户管理中的单用户配置，以及会话与重试设置中的用户配置区 |
| 生效对象 | 该用户的全部 API 令牌，以及其他使用同一用户身份的请求入口 |
| 生效范围 | 所有原本支持会话保持的模型和接口 |
| 可选状态 | 跟随系统策略、关闭会话保持 |
| 默认状态 | 跟随系统策略，兼容已有用户和新用户 |
| 保存时机 | 管理员明确点击保存后生效 |
| 恢复方式 | 改回“跟随系统策略” |

本期不增加用户级“强制开启”“优先保持”“严格保持”，也不扩展为按令牌、模型、分组或时间段配置，不提供批量操作和用户自助修改入口。

## 4. 核心业务规则

### 4.1 跟随系统策略

用户未配置或选择“跟随系统策略”时，完整沿用当前全局开关、规则匹配、规则模式及历史规则兼容行为。

“跟随”不代表一定开启，也不代表只看全局默认模式；最终行为仍由现有规则决定。

### 4.2 关闭会话保持

用户选择关闭后：

1. 不使用已有会话绑定选择渠道。
2. 不创建、更新或续期会话绑定。
3. 不因会话规则中的严格保持或旧版“失败不重试”配置而阻止正常重试。
4. 不因历史绑定渠道不可用而返回严格会话绑定错误。
5. 每个新的独立请求按现有渠道资格、用户渠道优先级、全局优先级和权重等规则进行调度。
6. 既有重试次数、错误分类、固定渠道限制等仍然有效；关闭会话保持不等于所有错误都必须重试。

**关闭会话保持不保证每次使用不同渠道。** 如果正常调度连续选中同一渠道，或只有一个可用渠道，仍可使用同一渠道。

### 4.3 策略优先级

用户级关闭应覆盖任何匹配规则中的会话保持行为，但不能绕过渠道访问资格、固定渠道和任务关联等必要约束。

| 全局开关 | 用户配置 | 匹配规则 | 预期行为 |
| --- | --- | --- | --- |
| 关闭 | 跟随系统策略 | 任意 | 关闭会话保持 |
| 关闭 | 关闭会话保持 | 任意 | 关闭会话保持 |
| 开启 | 跟随系统策略 | 优先保持 | 按现有优先保持行为执行 |
| 开启 | 跟随系统策略 | 严格保持或旧版失败不重试 | 按现有严格保持行为执行 |
| 开启 | 跟随系统策略 | 关闭 | 关闭会话保持 |
| 开启 | 关闭会话保持 | 任意，包括严格保持 | 关闭会话保持，恢复正常调度与重试判断 |
| 开启 | 任意 | 未匹配任何规则 | 正常调度，不建立会话绑定 |

### 4.4 保留规则附带配置

用户级关闭只改变会话绑定行为。全局会话功能开启、且规则仍然匹配时，规则中的请求头透传、参数覆盖等附带配置继续按现有逻辑生效。

例如，关闭某用户的会话保持后，原本依赖会话规则透传的客户端请求头仍应正常透传，避免功能开关意外改变请求兼容性。

全局开关关闭时，继续保持当前全局关闭语义。

### 4.5 历史绑定与恢复

- 关闭后立即忽略该用户请求可能命中的历史绑定，无需等待绑定过期。
- 不主动删除现有绑定，不清空全局或整条规则的缓存。
- 关闭期间的请求不得读取绑定结果用于调度，也不得写入、刷新或删除绑定。
- 恢复“跟随系统策略”后，重新执行现有规则；仍在有效期内的历史绑定可以被再次使用，已过期则重新建立。

当前绑定键不保证按用户独立隔离，因此不能通过清空命中的缓存来实现用户级关闭，否则可能影响其他用户。

### 4.6 生效时机与长连接

- 保存成功后，新的独立请求必须使用新配置，无需重启服务、重新登录或重新生成 API 令牌。
- 已经开始处理的请求沿用开始处理时的配置，不中途切换渠道。
- HTTP 普通请求和流式请求均适用。
- Responses WebSocket 在新连接首次选路时应用配置；已建立连接保持原有连接内的渠道约束，重新连接后应用新配置。
- 任务查询、后续操作等必须访问原渠道的关联行为保持有效。
- 多实例部署中，保存成功后的新请求应在所有实例获得一致配置。只有持久化和必要的缓存同步完成后才能提示成功。
- 若已落库但缓存同步失败，必须明确提示“配置已保存，生效同步失败”，允许回读真实状态并重试同步，不能误报完全成功，也不能声称数据库写入已回滚。实施时必须确定并验证旧缓存失效与恢复机制。

### 4.7 双入口与配置一致性

- 两个入口修改同一用户的同一份配置，复用相同的用户级读写接口和业务校验。
- 用户例外不得在全局会话规则或全局选项中再保存一份名单，避免产生两个配置来源。
- 任一入口保存成功后，应刷新对应用户详情和用户例外列表；其他已打开页面重新获得焦点或重新打开弹窗时读取最新状态。
- 未提交的编辑不因后台刷新而静默丢失；提交时如配置已被其他管理员或标签页修改，应提示冲突并要求重新加载，避免旧值无提示覆盖新值。
- 每次变更只针对一个用户，不通过提交整份例外名单替换已有配置，不影响其他管理员对不同用户的修改。

## 5. 管理界面

提供以下两个入口。

### 5.1 用户管理入口

**用户管理 → 指定用户的操作菜单 → 会话保持**。

弹窗展示目标用户的用户名和 ID，提供单选项：

| 选项 | 说明文案 |
| --- | --- |
| 跟随系统策略（默认） | 按系统会话规则决定是否保持渠道 |
| 关闭会话保持 | 该用户的请求不复用会话绑定，按正常渠道规则调度 |

### 5.2 会话与重试设置入口

**系统设置 → 请求策略 → 会话与重试 → 用户配置**。

新增独立“用户配置”卡片，放在会话规则之后、重试配置之前，保留现有默认设置、会话规则、重试配置之间的相对顺序。

卡片说明：默认所有用户跟随系统策略；下方列出单独关闭会话保持的用户。

卡片提供：

- **例外用户列表**：仅展示配置为“关闭会话保持”的用户，包含用户 ID、用户名、当前配置和操作；支持按用户 ID 或用户名搜索及服务端分页，不一次加载全部用户。
- **添加用户配置**：按用户 ID 或用户名搜索用户，选择一个用户后打开与用户管理入口相同的配置弹窗，默认选中“关闭会话保持”，点击保存后才写入。
- **编辑**：从列表打开相同配置弹窗；改为“跟随系统策略”并保存后，该用户从例外列表移除，不删除用户账号。
- **重复添加**：同一用户只能出现一次。选择已配置用户时进入其现有配置，不能生成重复记录。
- **空状态**：无例外时显示“所有用户均跟随系统策略”；搜索无结果时显示搜索空状态；加载失败独立展示重试入口，不能误显示为空列表。

用户搜索仅返回选择需要的用户 ID、用户名和当前策略，不扩大用户资料的可见范围。已删除用户不能新增或继续修改，不展示为可操作例外。

### 5.3 保存与交互边界

- 提供“取消”“保存”操作，取消不写入任何配置。
- 目标值与已保存值相同时不允许重复保存；新增例外虽然默认选中“关闭”，仍属于从“跟随”到“关闭”的变更，应允许保存。保存中防止重复提交。
- 保存成功后提示成功，再次打开时显示已保存值。
- 加载或保存失败时明确提示，不把未保存的值展示成已生效。
- 用户配置在弹窗中单独保存，并明确标注“单独保存，保存后生效”。页面原有全局“保存设置”仅保存全局会话与重试设置，不提交或覆盖用户配置。
- 保存用户配置、刷新例外列表时，保留页面尚未提交的全局设置；保存全局设置时，也不得重置用户配置。
- 用户配置区对全局开关的生效说明以服务端已保存值为准；页面存在未保存的全局修改时，应提示需保存全局设置后才会改变系统行为。
- 全局功能关闭时仍允许预先配置用户例外，并提示当前全局已关闭；以后全局开启时，该用户仍保持关闭。
- 两个入口的用户配置查询、搜索和修改使用一致的服务端权限规则，建议沿用用户渠道优先级的路由管理权限；能打开系统设置不自动获得用户配置管理权限。缺少权限时不展示可操作入口，直接调用接口也必须被拒绝。
- 所有界面文案支持项目现有的七种语言。

### 5.4 组件复用

复用已有用户操作菜单、`SettingsCard`、共享 `Dialog`、表单和数据表格能力。两个入口共享同一个用户会话配置弹窗及数据请求，新增功能组件只承载用户例外业务。本期不合并或重做现有用户渠道优先级界面。

现有渠道优先级弹窗面向渠道排序，不能直接承载用户会话策略；现有用户列表搜索可复用请求和分页行为，但返回字段及权限需按本节约束收敛。实施前继续检查共享表格的嵌入方式，避免把整页布局或页脚带入设置卡片。

## 6. 配置与可追踪性

- 配置持久化，服务重启后保留；缺失配置按“跟随系统策略”处理。
- 修改该项不得覆盖用户其他设置；用户修改语言、通知等个人设置时，也不得清除管理员设置的会话保持策略。
- 管理审计记录操作者、目标用户、修改前后值和修改时间。
- 管理员查看请求路由记录时，应能区分“用户级关闭”“全局关闭”“规则关闭”和“未匹配规则”。
- 复用现有日志和审计能力，不增加单独的日志页面，不记录完整会话标识、API 密钥等敏感内容。
- 存储位置、字段名称和接口地址在实施设计阶段确定，本需求不预先限定。

## 7. 验收标准

| 编号 | 场景 | 验收结果 |
| --- | --- | --- |
| A01 | 升级后未配置的老用户，以及新建用户 | 均默认跟随原有系统策略 |
| A02 | 全局开启，规则为严格保持，用户 A 单独关闭 | A 不受历史绑定影响，正常调度；其他用户行为保持原状 |
| A03 | 已有绑定指向不可用渠道，随后关闭该用户会话保持 | 新请求不因该绑定不可用而失败 |
| A04 | 用户关闭后，请求失败且符合既有重试条件 | 按既有重试规则处理，不被严格保持或旧版失败不重试阻止 |
| A05 | 用户关闭后连续发送相同会话标识的请求 | 不读取绑定用于选路，不创建、刷新或删除绑定；允许正常调度选中相同渠道 |
| A06 | 同一用户使用不同 API 令牌、模型或可用分组 | 用户级关闭一致生效 |
| A07 | 用户关闭，但命中带有请求头透传或参数覆盖的规则 | 附带配置继续按现有逻辑生效 |
| A08 | 用户已有渠道优先级，或请求存在固定渠道、任务关联 | 原有优先级和必要约束继续有效 |
| A09 | 用户恢复跟随系统策略 | 按现有规则执行，允许复用仍有效的历史绑定 |
| A10 | 全局关闭期间将用户设置为关闭，再开启全局功能 | 该用户继续关闭，其他用户按原规则执行 |
| A11 | 保存后使用原 API 令牌发送新 HTTP 请求或建立新 WebSocket 连接 | 应用新配置，无需重启或换令牌；现有连接不强制中断 |
| A12 | 用户修改语言、通知等设置，或管理员修改其他用户属性 | 会话保持配置保留，其他设置不被覆盖 |
| A13 | 普通用户、缺少相应权限的管理员直接调用管理接口 | 服务端拒绝修改，配置不变 |
| A14 | 保存失败、刷新页面、服务重启，以及多实例访问 | 不误报生效；成功保存的配置可回读、持久保留且一致应用 |
| A15 | 查看操作审计和请求路由记录 | 能识别配置变更和用户级关闭原因，其他用户共享的绑定不受影响 |
| A16 | 在任一入口修改同一用户，再到另一入口查看 | 读取相同的已保存值；恢复跟随后从例外列表移除 |
| A17 | 在会话与重试设置中搜索、添加、编辑例外用户 | 新增时默认关闭且可保存；搜索及分页有效，重复选择不产生重复记录，空状态与错误状态可区分 |
| A18 | 页面存在未保存的全局修改，此时保存用户配置；或反向操作 | 两类保存互不覆盖，不丢失未提交的全局修改 |
| A19 | 只有部分管理权限的管理员从两个入口操作或直接调用接口 | 用户查询、搜索和修改均遵守统一权限，不通过系统设置入口扩大权限 |
| A20 | 不同管理员分别修改不同用户，或同时修改同一用户 | 不同用户互不覆盖；同一用户的过期提交提示冲突，不静默覆盖 |
| A21 | 配置落库后缓存同步失败 | 显示部分完成状态，可回读并重试同步；恢复后各实例一致生效 |
| A22 | 搜索或编辑期间用户被删除 | 返回明确提示，不能创建无效例外，刷新后不保留可操作条目 |

实现阶段至少覆盖上述核心行为的针对性回归。若实现涉及数据库读写或模型变化，按项目要求在真实 SQLite、MySQL、PostgreSQL 上验证；若影响独立模块，执行对应模块独立构建。

## 8. 计划评审结论

结论：需求方向可行；已补齐双入口和保存边界。以下风险已写入需求及验收标准，需在实施中逐项验证，本次文档评审不代表功能已实现。

| 优先级 | 发现的问题 | 本版处理 |
| --- | --- | --- |
| P1 | 双入口若各自维护名单，会出现策略不一致或整表覆盖 | 同一用户配置来源、同一接口、单用户增量修改和冲突检测，见 4.7、A16、A20 |
| P1 | 当前会话与重试使用全局表单保存，直接嵌入用户名单易混淆保存时机、丢失未保存设置 | 独立卡片与弹窗保存，全局保存不包含用户配置，见 5.3、A18 |
| P1 | 在会话匹配入口直接跳过，会同时丢失透传模板；只跳过缓存读取又可能继续写绑定或阻止重试 | 保留规则附带配置，同时覆盖绑定读写及重试行为，见 4.2、4.4、A04、A05、A07 |
| P1 | 当前个人通知设置会重新构造并写入设置对象，若将策略放入同一对象，可能被后续个人设置清除；并发整对象写入也可能覆盖 | 存储设计须隔离或安全合并管理员策略，覆盖个人设置及并发回归，见第 6 节、A12、A20 |
| P1 | 新增系统设置入口可能沿用页面权限，从而绕过用户配置管理权限 | 两入口统一查询、搜索、写入权限，见 5.3、A19 |
| P2 | “立即生效”未区分落库、缓存同步和已有长连接，失败时容易误报成功 | 明确新请求、连接快照和部分失败语义，见 4.6、A11、A21 |
| P2 | 仅在前端过滤或一次拉取全部用户，无法保证大用户量下可用 | 服务端查询、分页、最小返回字段，见 5.2、A17 |

## 9. 建议实施顺序与验证

1. **用户配置与管理接口**：确定持久化位置、单用户冲突检测、统一权限和缓存同步机制；提供用户策略读写、例外列表及用户搜索能力。先验证持久化、跨实例一致性、并发和其他个人设置不覆盖策略。
2. **请求策略接入**：在统一策略边界应用用户级关闭，覆盖规则模式、绑定读写和重试判定；保留模板及固定渠道、任务关联约束。集中扩展合适的现有回归测试，避免跨层重复测试。
3. **双入口界面**：先完成共享配置弹窗，再接入用户菜单和会话与重试卡片，覆盖独立保存、列表刷新、冲突及错误状态，并补全七种语言。
4. **验收**：完成表中针对性回归；前端执行类型检查、涉及文件 lint、相关测试和生产构建；按实际存储及模块变更完成真实三数据库验证和独立模块构建。

验证范围调整：按用户后续明确要求，本次使用 SQLite 验证，不操作 Docker，不作 MySQL、PostgreSQL 的兼容性验证结论。跨连接一致性通过两个独立 SQLite 连接验证，未部署多实例服务进行端到端验证。

## 10. 实施采用的产品口径

本次采用以下四个产品决定：

1. 由管理员配置，普通用户不提供自助开关。
2. 对整个用户生效，覆盖其所有令牌、模型和适用接口。
3. 只有“跟随系统策略”和“关闭”两种状态。
4. 关闭时忽略历史绑定，恢复后允许复用仍未过期的绑定；已有 WebSocket 连接在重连后应用新配置。

## 11. 实现与验证记录

### 实现结果

- 用户管理菜单与会话与重试卡片均已接入，共享编辑弹窗、接口和查询缓存；用户例外可搜索、分页、新增和恢复跟随。

- 用户策略不另设 Redis 或本机缓存。每个请求首次选路时增加一次数据库读取，随后保持请求内快照；因此用户策略没有保存后的缓存同步窗口，第 4.6 节和 A21 中的策略缓存部分失败场景不适用。
- 关闭策略覆盖规则严格模式及旧版失败不重试，不读取或维护绑定缓存；规则附带模板、用户渠道优先级、固定渠道和 WebSocket 资格约束保持有效。

- 新增界面与日志文案已补齐七种语言。
- 已修复评审发现的两项同步问题：用户详情及例外列表在窗口重新聚焦时始终刷新；查询传递取消信号，并由 React Query 管理共享请求，确保保存后的刷新不会复用 Axios 中保存前的在途响应。后台刷新仍保留编辑中的选择与原始版本，以便检测冲突。
