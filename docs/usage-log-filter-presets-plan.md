# 使用日志多筛选方案开发计划

版本：v1.0

日期：2026-10-17

状态：已实现，已完成 SQLite 与相关前后端自动化验证；MySQL/PostgreSQL 实例验证未执行

## 1. 目标与范围

为使用日志增加账号级、多方案的筛选配置管理能力。用户可以保存多份命名方案、自由切换，并指定默认方案。同一账号在不同浏览器、设备登录后，可以读取和使用服务端保存的方案。

本期覆盖普通使用日志（`common`），存储和接口保留日志类别维度。每个账号在“全部”和“仅自己”两个有效查看范围内分别管理方案。

核心定义：

- **当前方案**：用户当前正在查看、编辑或准备应用的方案。
- **默认方案**：普通进入页面且没有明确 URL 条件时，自动使用的个人方案。
- **系统默认**：内置的默认筛选，可选择、可设为默认，不能覆盖或删除。
- **临时筛选**：没有关联有效个人方案的一组筛选条件，可以查询或另存为个人方案。
- **重置筛选**：恢复当前个人方案的最新保存值；当前为临时筛选时恢复账号默认方案，没有个人默认时恢复系统默认。

切换方案不自动修改账号默认方案。保存配置与执行查询是独立操作。

## 2. 保存内容

### 2.1 允许保存的筛选字段

| 字段 | 含义 | 使用约束 |
| --- | --- | --- |
| `model` | 模型筛选 | 沿用现有匹配规则 |
| `group` | 分组筛选 | 沿用现有日志筛选能力 |
| `type` | 日志类型 | 使用现有单选类型及“全部类型” |
| `token` | 令牌名称 | 保存名称筛选值 |
| `username` | 用户名 | 仅在有权限的查看范围使用 |
| `excludeUsername` | 排除用户名 | 仅在有权限的查看范围使用 |
| `channel` | 渠道 ID | 沿用现有管理范围限制 |
| `requestId` | 请求 ID | 沿用现有匹配规则 |
| `upstreamRequestId` | 上游请求 ID | 沿用现有匹配规则 |

后端采用明确的字段白名单，并校验类型、枚举及长度。恢复时依据当前权限过滤不可使用的字段；历史资源名称不因当前下拉选项中不存在就被自动删除，以免改变历史日志查询含义。

### 2.2 不随方案保存的状态

- 固定开始、结束日期。
- 页码、每页条数、表格列显示、列宽和布局。
- 尚未执行查询的其他页面状态。

应用方案、重置或恢复系统默认时，调用现有时间范围逻辑重新计算时间。用户手动选择的日期仅用于当前临时查询，界面需要说明“时间范围不随方案保存”。

仅修改日期不算方案内容发生修改，不应提示日期已保存。切换方案会重新计算默认时间；重置按钮仍允许用来恢复日期。

### 2.3 名称和容量约束

以下为本计划建议采用的首版约束：

- 名称去除首尾空白后必填，长度为 1–40 个 Unicode 字符。
- 同一账号、日志类别和有效查看范围内，名称按服务端统一的大小写不敏感规则比较，不允许重名。
- 每个账号、类别和查看范围最多保存 20 份个人方案；系统默认不占名额。
- 文本筛选值最多 256 个 Unicode 字符，完整筛选 JSON 最多 8 KiB；渠道 ID 和日志类型另做格式、枚举校验。
- 允许保存没有附加条件的具名方案。它具有自己的 ID、名称和版本，与系统默认保持不同身份。

## 3. 用户操作

| 操作 | 配置变化 | 页面查询行为 |
| --- | --- | --- |
| 查询 | 不修改保存内容 | 应用当前表单，回到第一页并刷新日志及统计 |
| 选择个人方案 | 不修改方案和默认指向 | 读取并应用方案最新内容，回到第一页并查询 |
| 选择系统默认 | 不修改个人默认指向 | 应用系统默认条件，回到第一页并查询 |
| 保存筛选设置 | 更新当前个人方案；临时筛选或系统默认状态下提示命名新建 | 保留当前查询结果，查询按钮继续负责应用表单 |
| 另存为新方案 | 使用当前可保存字段创建新方案，成功后选中新方案 | 保留当前查询结果 |
| 重置筛选 | 不修改保存内容 | 读取恢复目标的最新值，重新计算时间，回到第一页并查询 |
| 重命名 | 只修改名称，递增方案版本 | 不改变当前查询 |
| 设为默认 | 更新当前范围的默认方案指向 | 不改变当前查询 |
| 将系统默认设为默认 | 清除个人默认指向，保留所有个人方案 | 不改变当前查询 |
| 删除当前个人方案 | 删除该方案，必要时清除默认指向 | 成功后应用剩余的账号默认方案；没有则应用系统默认，再查询 |

新建、另存和普通切换不会自动设置账号默认方案。创建后可使用“设为默认”，决定下次普通进入页面使用哪一份。

此前讨论的“清除已保存设置”由“删除当前方案”承接，删除范围仅限选中的个人方案。

### 3.1 重置按钮规则

- 选中个人方案：恢复该方案的服务端最新保存值。
- 选中系统默认：恢复系统默认，不切换到个人默认方案。
- 处于临时筛选状态：恢复账号默认方案，没有个人默认时恢复系统默认。
- 当前条件为空、仅日期变化或当前方案没有附加条件时，重置仍可用。
- 加载必要配置或正在执行互斥操作时暂时禁用，不能继续使用“当前是否有筛选条件”作为唯一禁用依据。
- 读取成功后统一更新表单、URL、页码、日志和统计；读取失败时保留原状态并提示重试。
- 手机抽屉在重置成功后关闭，失败时保持打开。

### 3.2 未保存修改

当前可保存字段与编辑基线不同时，显示“有未保存修改”。带着这些修改切换方案时，提供：

1. 保存后切换：保存成功后才切换；当前为临时筛选时先完成命名创建。
2. 放弃修改并切换。
3. 取消切换，继续编辑。

保存失败或发生版本冲突时，保留草稿和当前方案，不继续切换。

## 4. 首次进入、URL 与查看范围

### 4.1 应用优先级

**URL 明确筛选条件 → URL 指定的合法个人方案或系统默认 → 账号默认方案 → 系统默认。**

| 进入场景 | 处理方式 |
| --- | --- |
| 无明确 URL 筛选或方案参数 | 读取当前账号、类别和有效范围的默认方案，再首次查询 |
| URL 只有页码、每页条数 | 仍加载账号默认方案；分页参数不代表显式筛选 |
| URL 指定个人方案 ID，没有明确条件 | 校验方案归属及范围，读取方案后应用 |
| URL 明确指定系统默认 | 应用系统默认，保留明确选择的语义 |
| URL 有明确条件，没有方案 ID | 使用整组 URL 条件，标记为临时筛选；保存时新建方案 |
| URL 同时有合法方案 ID 和明确条件 | 使用整组 URL 条件，以该方案为保存基线；内容不同时显示未保存修改 |
| URL 的方案已删除、无权访问或范围不匹配，且有明确条件 | 保留合法 URL 条件为临时筛选，提示方案不可用 |
| URL 的方案不可用，且没有明确条件 | 提示方案不可用，再恢复当前范围默认方案或系统默认 |

“明确条件”按合法筛选参数判断，不能简单检查解析后的 search 对象是否有字段。显式“全部类型”属于有效条件；无效参数不得被当作有效方案内容。

URL 条件作为一组使用，不隐式叠加保存方案中的模型、分组等条件。未明确给出的时间使用系统默认时间。

有明确 URL 条件时，可以先按这些条件查询，方案列表及编辑基线独立加载；相关基线尚未读取成功时，不允许覆盖保存。无明确条件时，默认方案初始化必须成为日志和统计首次查询的前置步骤，避免先查系统默认再跳到个人方案。

### 4.2 有效查看范围

- 普通用户及管理员“仅自己”统一使用 `self`。
- 有权限的管理员“全部”使用 `all`。
- 以实际可访问范围计算配置键，不能直接使用页面内部默认可能为 `all` 的原始状态。
- 切换查看范围后，应用目标范围对应的默认方案；存在未保存修改时先走切换确认。
- 切换账号、日志类别或查看范围时，旧异步请求不得更新新范围的界面。

## 5. 跨设备同步与编辑状态

前端应区分三份数据：**已经应用的查询、正在编辑的表单、方案保存基线**。

保存基线必须同时包含方案 ID、内容和版本号。管理员或其他设备修改方案后：

- 页面重新聚焦时刷新方案列表、默认指向和最新服务端信息。
- 当前已经应用的查询和编辑表单保持不变，可以提示方案已有更新。
- 保留原编辑基线的内容及版本号，不得把旧草稿和后台读到的新版本号组合提交。
- 用户明确重置、重新加载或保存成功后，才将编辑基线更新为相应的服务端结果。
- 仅因默认方案在其他设备改变，不自动替换当前正在查看的方案。

URL 反映已应用的查询；保存、重命名和设置默认不把尚未查询的草稿写入 URL。

### 5.1 远程删除

当前方案被其他设备删除时：

- 提示方案已删除，当前条件转为临时筛选。
- 保留当前表单和查询结果，允许另存为新方案。
- 停止向已删除的 ID 提交更新。
- 用户点击重置时重新读取账号默认指向，恢复有效默认方案或系统默认。

### 5.2 请求与缓存

- React Query 的配置查询键包含账号、日志类别、有效范围，以及必要的方案 ID。
- 列表和详情显式启用窗口聚焦刷新，覆盖应用默认关闭聚焦刷新的设置。
- 传递取消信号，避免切换范围、方案或保存后，旧响应覆盖新结果。
- 沿用已验证的会话配置查询方式，由 React Query 管理查询共享；配置读取绕过 Axios 中可能复用保存前请求的额外去重。
- 保存、重命名、删除、设置默认成功后刷新对应列表、详情及默认指向。
- 重置读取最新服务端结果，不能只恢复页面进入时的本地缓存。

## 6. 服务端存储设计

配置独立存储，避免个人通知等设置整份重写时覆盖筛选方案。首版无需引入额外 Redis 配置缓存。

### 6.1 筛选方案表

建议模型：`UserLogFilterPreset`。

| 字段 | 用途 |
| --- | --- |
| `id` | 数据库生成的稳定方案 ID |
| `user_id` | 所属账号 |
| `category` | 日志类别，首版支持 `common` |
| `scope` | 有效查看范围：`self` / `all` |
| `name` | 显示名称 |
| `name_key` | 服务端规范化名称的稳定唯一键 |
| `filters` | `TEXT` 存储的筛选 JSON |
| `version` | 乐观并发控制版本 |
| `created_at` / `updated_at` | 创建及修改时间 |

按账号、类别、范围及名称键建立唯一约束。名称键的表示需要避免数据库排序规则差异，例如使用规范化名称的稳定摘要。

### 6.2 默认方案设置表

建议模型：`UserLogFilterPreference`。

| 字段 | 用途 |
| --- | --- |
| `user_id`、`category`、`scope` | 唯一确定一组个人方案 |
| `default_preset_id` | 可空，空值表示使用系统默认 |
| `version` | 默认指向的并发控制版本 |
| `updated_at` | 最近修改时间 |

取消个人默认时保留该设置记录及版本号。每个范围通过单一默认指向保证最多一份默认方案。

### 6.3 写入约束

- 用户 ID 从登录上下文获取，不接受客户端指定其他账号作为操作对象。
- 更新、重命名和删除校验方案版本；设置默认校验默认设置版本。
- 新建与改名同时依赖服务端校验和数据库唯一约束，避免并发重名；数量上限检查与创建放在同一事务内。
- 默认方案必须属于同一账号、类别及范围。
- 删除方案与清除指向该方案的默认设置在同一事务中完成，清除默认指向时递增设置版本。
- 已删除方案的旧更新返回不可用，不通过更新接口重建旧 ID。
- 账号删除时清理其方案与默认设置；清理应复用现有用户数据删除事务边界。
- JSON 编解码使用根模块 `common.*` 包装；保持 SQLite、MySQL、PostgreSQL 的通用存储设计。

## 7. 接口计划

以下路径为建议命名，实现时与项目路由约定统一：

| 方法与路径 | 功能 |
| --- | --- |
| `GET /api/user/self/log-filter-presets` | 按类别和范围读取方案列表、默认方案 ID 及默认设置版本 |
| `GET /api/user/self/log-filter-presets/:id` | 读取本人方案详情及版本 |
| `POST /api/user/self/log-filter-presets` | 新建命名方案，返回创建结果及版本 |
| `PATCH /api/user/self/log-filter-presets/:id` | 按版本更新筛选内容或名称 |
| `DELETE /api/user/self/log-filter-presets/:id` | 按版本删除方案，返回最新默认指向及设置版本 |
| `PUT /api/user/self/log-filter-default` | 按默认设置版本指定方案，或设为系统默认 |

接口复用现有登录校验，并登记个人资料读写对应的访问令牌权限。方案归属、范围权限和字段权限均由服务端校验；保存方案不能扩大日志查询权限。

返回值明确区分：成功读取空列表、方案不可用、版本冲突、名称冲突、达到数量上限、参数错误，以及真实的读取或写入失败。具体错误码沿用项目命名方式，前端提供对应的本地化反馈。

## 8. 界面与失败处理

- 桌面端主操作区提供方案选择器、保存筛选设置、重置筛选；更多菜单提供另存、重命名、设为默认和删除。
- 选择器标明当前方案、默认标记及未保存修改；系统默认始终有独立选项。
- 命名、删除确认和未保存修改确认复用项目共享弹窗及表单组件。
- 手机筛选抽屉提供相同能力，异步操作成功后再按操作语义关闭抽屉。
- 保存失败不更新保存基线、不丢草稿；删除失败不移除列表项；重置失败不清空条件。
- 读取失败不能伪装成空列表或“没有默认方案”。普通入口可提供明确的“临时使用系统默认”操作，供用户主动继续查询，该操作不修改服务端配置。
- 恢复时如果存在当前权限不可使用的字段，提示已忽略；后台读取不能因此自动回写、删减保存内容。
- 所有新文案覆盖现有七种语言。

## 9. 实施顺序

### 阶段一：数据与接口

新增独立模型及迁移、字段与名称校验、本人 CRUD、默认指向及并发控制；接入权限声明和用户删除清理。先验证数据隔离、唯一约束和原子性。

### 阶段二：统一筛选状态

在使用日志模块中统一处理账号、有效查看范围、URL 来源、方案保存基线、表单草稿和已应用查询。日志列表、统计和筛选栏共用解析结果，完成首次加载、重置及范围切换。

### 阶段三：多方案界面

扩展已有 `LogsFilterToolbar`、普通日志筛选栏及移动端抽屉，加入方案选择和管理操作；复用共享选择、弹窗、确认和错误状态组件，并补齐翻译。

### 阶段四：同步与回归

覆盖多标签页、多设备修改、聚焦刷新、过期响应、保存冲突及远程删除；执行相关前后端测试、类型检查、lint、格式检查和构建。

## 10. 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 新用户无个人方案进入页面 | 使用系统默认，加载结果明确为空列表 |
| A02 | 新建、改名、另存 | 内容和名称正确持久化，ID 稳定，修改版本递增 |
| A03 | 同一账号在另一浏览器进入 | 读取同一组方案，并应用指定默认方案 |
| A04 | 切换不同个人方案 | 表单、URL、日志与统计一致，页码回到第一页 |
| A05 | 保存当前表单但不点击查询 | 方案已保存，当前查询结果与 URL 保持原状 |
| A06 | 临时修改后重置 | 恢复当前方案服务端最新值，时间重新计算 |
| A07 | 清空全部条件或仅修改日期后重置 | 重置仍可执行，恢复目标正确 |
| A08 | 将系统默认设为默认 | 个人方案全部保留，下次普通进入使用系统默认 |
| A09 | 删除当前方案或默认方案 | 默认指向无悬空，成功后正确回退并查询 |
| A10 | 其他设备删除当前方案 | 当前条件保留为临时筛选，可另存，旧 ID 无法更新 |
| A11 | 带未保存修改切换 | 保存后切换、放弃、取消均符合定义；保存失败不切换 |
| A12 | 后台刷新遇到其他设备更新 | 不覆盖草稿，不推进旧草稿的基线版本；过期保存提示冲突 |
| A13 | 并发设置默认、删除默认方案 | 始终保持单一合法默认指向，冲突可见 |
| A14 | URL 只有分页参数 | 应用个人默认方案，不误判为明确筛选 |
| A15 | URL 带条件但无方案 ID | 使用临时筛选，保存时新建，不覆盖个人默认方案 |
| A16 | URL 同时带方案与条件 | 使用整组 URL 条件，保存目标及未保存标记正确 |
| A17 | URL 指定不可用或其他账号的方案 | 不泄露方案内容，按既定规则提示与回退 |
| A18 | 首次配置加载缓慢或失败 | 不先查询错误条件；失败不会被当作未保存 |
| A19 | 保存、重置、删除失败 | 原配置、草稿和查询状态按操作语义保留，手机抽屉不会误关闭 |
| A20 | 保存前请求在保存后才返回 | 旧响应不覆盖新方案、列表或默认指向 |
| A21 | 普通用户、管理员范围切换、账号切换或权限降低 | 配置和缓存正确隔离，服务端权限有效，旧请求不污染新范围 |
| A22 | 空方案、重名、空白名称、超长字段及超过数量上限 | 空方案可保存，其余非法输入明确拒绝；并发请求不绕过约束 |
| A23 | 电脑端与手机端操作 | 保存、切换、重置、管理及错误反馈语义一致 |
| A24 | 服务重启、新库及已有用户库升级、重复迁移 | 方案和默认指向保留，唯一约束及既有用户数据保持正确 |

数据库验证按用户此前要求使用真实 SQLite，覆盖新建、升级及重复迁移；本轮不使用 Docker。保留项目跨数据库设计约束，不把 SQLite 通过表述为已完成 MySQL、PostgreSQL 实例验证。

跨设备验收需要两个独立客户端会话或浏览器上下文，并使用真实服务端持久化结果。前端同步回归使用生产 QueryClient 和真实 HTTP 客户端，仅在网络边界控制响应顺序，不通过替换整个 API 方法掩盖取消或去重行为。
