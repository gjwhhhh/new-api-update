# Cyber 会话封禁后的可配置备用渠道计划

更新时间：2026-11-23（Asia/Taipei）

状态：已在独立工作树实现，三个代码 Review 问题已修复并完成回归；全量测试仍有一项已复现的基线失败。本功能通过独立分支交付，尚未打包或部署。实际验证范围和边界见第 13 节。

## 1. 目标与结论

当请求命中已有 Cyber 会话封禁时，管理员可以选择继续拦截，或者将符合条件的请求交给一个指定的备用渠道。原封禁保留，不通过解除封禁实现转送。

架构上沿用现有渠道选择、上游执行、计费和审计链路。Cyber 只提供处理决策，渠道选择层执行候选范围限制，不在 Cyber 中间件里请求备用上游，不递归调用 Relay，也不复制计费或重试逻辑。

第一版不是“所有会话均可无感切换”：只在请求不依赖不可迁移的上游状态、且原有访问规则允许时转送。已建立的 WebSocket 和有状态续接存在明确限制。

### 1.1 第一版包含

- 现有 Cyber 策略页面配置“直接拦截 / 转到备用渠道”，以及一个备用渠道。
- 已封禁会话的后续 HTTP 请求，以及尚未建立上游连接的 Responses WebSocket 请求。
- 在现有支持范围内接入普通 Relay 和任务插件 Responses 路径，统一执行安全检查。
- 备用渠道再次 Cyber 拒绝后的批次级限制、成功及失败路由记录。
- 旧策略、旧封禁记录的兼容，以及配置、日志和 Redis 状态的回归验证。

### 1.2 第一版不包含

- 首次上游 Cyber 失败后，在同一个请求内立即重发到备用渠道。
- 多个备用渠道、多级转送、竞速或新的负载均衡算法。
- 已建立 WebSocket 的无感上游连接迁移。
- 自动删除 `previous_response_id`、重建完整历史，或重放已经开始执行的任务、工具及输出。
- 借转送绕过本地内容检查、令牌权限、分组、模型或原任务归属限制。
- 扩大当前 Cyber 的会话识别范围，或改变全站 Redis 故障处理策略。

## 2. 已核对的现状与实现风险

以下保留方案评审时的基线事实；实施结果和验证记录见第 13 节。

| 位置 | 现状 | 本次约束 |
| --- | --- | --- |
| `service/cyber_session_guard.go` | 全局/令牌范围可在选路前直接拒绝；渠道范围在已知渠道后检查 | 拆开“封禁状态判断”和“拒绝/转送决策”，不能仅删除拒绝返回 |
| `service/channel_select.go` | 强制渠道、普通亲和和随机渠道池走不同分支 | 不用新增高优先级强制渠道绑定来实现备用路由 |
| `controller/relay.go` | HTTP 重试可直接调用渠道池，不完全经过首次选路入口 | 约束必须对首次选路、直接渠道池调用和后续重试均有效 |
| `relay/responses_websocket.go` | 已连接会话固定渠道、模型和凭据，并恢复连接上下文 | 首次连接与已有连接分别处理，不只替换渠道 ID |
| `service/cyber_bans.go` | 封禁有批次信息及基于原值校验的撤销；兼容历史值 `1` | 不破坏原值校验；备用拒绝状态不得污染下一批封禁 |
| `model/cyber_events.go` | 当前仅查询特定 Cyber 错误日志 | 成功转送需要显式记录和查询，不能伪装成失败 |
| `service/channel_affinity.go` | 亲和不满足条件时可能删除缓存，成功时可能写回 | 转送请求既不误删原亲和，也不把备用渠道写回普通亲和 |

当前会话识别依赖同一令牌及请求中的合法 `prompt_cache_key` UUID，并有请求体读取上限。缺少可识别会话等现有跳过场景，不会因为新增转送配置就自动获得封禁或迁移能力。`scope=all` 不代表跨令牌合并会话。

工作区存在其他未提交功能，部分与 Relay、Cyber、本地提示词过滤和前端设置重叠。实施时必须区分 HEAD 行为与这些本地修改，仅提交本计划相关改动，不还原或混入其他任务。

## 3. 配置与兼容

扩展现有 `CyberSessionPolicy`，继续通过现有 Cyber 策略 API 保存，不增加只能通过环境变量启用的隐藏开关。

| 建议字段 | 可选值/默认值 | 说明 |
| --- | --- | --- |
| `blocked_action` | `block` / `reroute`，默认 `block` | 命中有效封禁后的处理动作 |
| `fallback_channel_id` | 未设置 | 仅 `reroute` 时要求为一个有效渠道 ID |

- 保留现有 `off`、`shadow`、`enforce` 模式；只有 `enforce` 执行实际转送。`shadow` 只观察，不改变路由。
- 读取旧配置缺少新字段时，先归一化为 `block`，再验证；保存时写入规范化配置。
- 保存时校验备用渠道存在及基本状态；请求时仍重新验证权限、模型、接口、渠道状态和凭据可用性，不能只相信保存时检查。
- 继续保留超级管理员写入权限、保存确认、配置修改审计；管理员只读权限不扩大。
- 页面复用现有表单、渠道候选查询、选择控件和确认弹窗，并支持项目七种界面语言。
- 确认弹窗说明：会将本次请求携带的上下文发送给备用上游，成本、延迟及模型行为可能不同。
- 一个请求使用一致的策略快照；配置变更对之后的请求生效，不在调用中途切换目标。

## 4. 行为契约

| 条件 | 第一版结果 |
| --- | --- |
| 未封禁、未纳入范围或模式关闭 | 保持现有处理路径 |
| 观察模式命中 | 保持原路由，只记录观察结果 |
| 首次上游 Cyber 拒绝 | 保持原响应和封禁记录行为，不新增本次备用重试 |
| 命中已有封禁，动作是 `block` | 保持现有拦截行为及既有错误契约 |
| 命中已有封禁，动作是 `reroute`，且检查通过 | 只允许配置的备用渠道处理本次请求 |
| 备用渠道不支持模型、接口、执行模式或分组 | 明确失败，不绕回原渠道或其他随机渠道 |
| 强制渠道、严格会话绑定或原任务绑定与备用渠道冲突 | 明确失败，不静默覆盖绑定 |
| 备用渠道发生普通上游错误 | 沿用适用的错误处理；不因此解除原封禁，也不记录为新的 Cyber 拒绝 |
| 备用渠道再次 Cyber 拒绝 | 记录本批封禁下该备用渠道不可再用，后续请求不重复发送给它 |
| 备用渠道与已知原拒绝渠道相同 | 拒绝转送，避免以备用名义再次请求原拒绝渠道 |
| 原封禁到期或撤销，后续请求可独立执行 | 恢复普通选路 |
| 携带不能证明可在目标渠道解析的上游状态引用 | 明确拒绝迁移，不改写请求来伪造连续会话 |

历史封禁不一定保存原拒绝渠道。不得从缺失字段推断来源；兼容这类记录时需要在管理信息中标明来源未知。允许在其他检查通过后向配置目标发起一次正常尝试，但不能承诺这一定是不同于历史失败来源的渠道；若再次 Cyber，立即纳入备用拒绝限制。新封禁应补充可选的原拒绝渠道信息。

## 5. 路由层设计

### 5.1 决策与执行分离

1. Cyber 层识别会话并读取有效封禁，产出本请求决策：普通处理、直接拒绝、或限制到备用渠道。
2. 渠道选择层将备用候选集合与现有可用集合取交集，并处理硬绑定冲突、普通亲和及协议限制。
3. 选定最终执行渠道后，正常装载渠道上下文、选择凭据、校验内容，再进入现有执行和计费流程。
4. 请求结束时按实际结果记录路由事件、必要的备用拒绝状态以及正常用量/失败记录。

不添加能够覆盖令牌强制渠道或原任务渠道的 Cyber 高优先级 Pin。新增候选限制应表达稳定的领域概念，复用现有 `ChannelConstraints` 和过滤执行机制，不把 Cyber 配置判断复制进每个渠道适配器。

### 5.2 必须覆盖的入口

- HTTP 首次分发、普通 Relay 的后续渠道选择和重试。
- 任务插件 Responses 的选路、原任务绑定和提交前检查；不把“支持同名模型”当作可以跨插件执行的证明。
- Responses WebSocket 首次选路，以及已有连接遇到目标变更时的终止判定。
- 渠道范围封禁命中后的替代选择：必须在目标调用和预扣费之前完成，不将原候选算作已调用上游。

备用候选必须同时满足请求可用分组、模型能力、渠道启用及凭据状态、接口路径、插件归属/协议执行模式、WebSocket 能力等原有规则。自动分组不允许借备用配置扩大到未授权分组；记录实际使用分组，并保留原有跨组策略约束。

### 5.3 亲和与重试

- 普通会话亲和仅对当前转送请求让位；不触发原亲和缓存删除，也不套用原亲和渠道的专属参数覆盖。
- 备用成功不写入普通亲和缓存；转送信息使用本请求独立元数据，不修改全局亲和设置。
- 严格会话绑定、强制渠道和原任务归属不因转送而放宽。
- 不增加 Cyber 专属重试额度；已转送请求的任何既有重试都不能离开备用候选范围。
- 已提交流式事件、已执行工具或已接受的不可安全重放任务，不因备用失败而重新执行。
- 第一版不增加同一备用渠道的特殊重放机制；是否允许某次既有重试，继续受原错误分类、重放边界和绑定规则限制。

## 6. 上下文、WebSocket 与有效期边界

### 6.1 不能把“没有前序 ID”当作完整历史证明

可转送请求必须能够在目标执行环境独立解释。除了 `previous_response_id`，还需要识别持久会话引用、原任务、上游文件/资源引用、未配对工具结果等已知依赖。不确认归属的引用不能直接跨渠道转发，也不能从会话审计中拼接历史补救。

网关只能做协议和已知状态依赖检查，无法保证客户端提供了语义上完整的全部历史。页面和错误说明不能承诺网关会自动补齐缺失内容。

对新的 HTTP 请求或新 WebSocket 连接，第一版保守拒绝无法证明可迁移的有状态续接，包括客户端已经在备用渠道成功一次、随后仅凭前序响应 ID 续接的情况。不仅凭同一渠道 ID、相同 URL 或相同供应商品牌认定状态可共享，多凭据渠道也不例外。已经在备用渠道建立的同一条 WebSocket 连接按下一节处理，不属于跨连接迁移。

### 6.2 WebSocket

- 尚未建立上游连接，且首个请求满足独立执行条件时，可以选择备用渠道。
- 已建立连接的后续轮次如需更换渠道，返回明确的“需要重新连接/无法迁移上下文”原因，并有序结束受影响连接，不在原连接中热替换渠道或凭据。
- 客户端重连后仍必须提供可独立执行的上下文；不得假设客户端一定会自动重连或补发完整历史。
- 已经在备用渠道建立的连接，其后续合法轮次可以按现有同连接规则继续；但原封禁到期不触发切回原渠道。实际权限、渠道可用性仍按现有规则重新检查。
- 如果策略调整为直接拦截、当前备用连接不再被新策略允许，或备用已被记录为 Cyber 拒绝，不强行保持连接继续调用。

### 6.3 封禁到期或撤销

仅对能够独立执行的新请求恢复普通选路。已有 WebSocket 不因封禁到期自动迁移；有状态响应链若要支持在到期后继续留在备用渠道，需要独立的会话路由归属能力，不能把路由生命周期简单绑定为封禁 TTL。

该归属能力属于后续方案，第一版不隐式增加。产品验收必须区分“后续独立请求可转送”和“整个有状态会话无感迁移”。

## 7. 备用拒绝状态、并发与 Redis

### 7.1 生命周期

- 保留原封禁键和值的兼容性；备用拒绝状态另行关联原封禁批次和目标渠道，不用覆盖原封禁值的方式更新。
- 建议每批封禁关联一个独立的 Redis 备用拒绝集合；集合中的成员是已被 Cyber 拒绝的目标渠道 ID。命名空间与现有封禁列表扫描隔离。
- 临时封禁的集合继承父封禁剩余有效期，不能每次拒绝重置成完整 TTL。
- 永久封禁的关联集合必须随显式撤销清理；不能留下只能等待不存在的 TTL 过期的永久垃圾状态。
- 变更备用配置不删除原封禁，也不把 B 的拒绝错误套用到 C；改回已拒绝的 B 时，本批次内仍禁止再次发送。
- 集合设定明确容量上限；达到上限时停止本批次转送并提示管理员处理，不能为了腾空间删除旧拒绝成员再反复尝试。

### 7.2 并发与旧数据

- 读取封禁值、批次和剩余有效期时使用一致性操作；记录备用拒绝前原子验证父封禁仍属于同一批次。
- 撤销父封禁及其关联集合需要保持并发安全。撤销后的迟到失败不得复活旧封禁，也不能影响新创建的一批封禁。
- 支持现有元数据及历史值 `1`。历史值缺少唯一批次标识时，首次需要备用状态可通过原值比较的方式原子补齐唯一批次，并保留原过期时间；过期/撤销后重建不能重用旧批次。
- 历史记录补齐导致管理页面所持撤销版本失效时，沿用现有冲突语义，要求刷新后再操作，不能撤销未确认的新状态。
- 不持有数据库事务或全局渠道锁等待 Redis 网络往返；沿用有界超时，不逐个渠道发起无界 Redis 查询，不在请求路径 `SCAN`。
- 不承诺取消已经发往上游的其他并发请求；新的拒绝状态约束后续决策，不能宣称实现了每个会话的全局串行执行。

### 7.3 故障策略

第一版保留现有“无法读取封禁时跳过本次封禁判断”的兼容行为，因此 Redis 不可用时，不保证已封禁会话一定被拦截或转送。必须保留指标和告警，不把该限制隐藏在成功说明中。

如果本请求已经确认命中封禁，则不能因为后续备用状态检查失败而放回普通渠道。此时返回可识别的临时不可用错误；父封禁批次已变化时也不得套用过期决策。

备用 Cyber 拒绝的状态写入失败，需要保留原失败响应、记录错误及告警；后续请求可能再次尝试备用渠道，不能宣称存储失败时仍保证只尝试一次。若未来要求严格不漏拦截，需要另行评估封禁读取失败时拒绝请求的可用性影响，不在本次悄悄改变全站语义。

## 8. 日志、会话审计和计费

### 8.1 可观测性

- 使用独立的路由决策元数据记录：原封禁批次、会话指纹、已知原拒绝渠道、目标渠道、实际执行渠道/分组、动作、结果和原因、请求 ID。
- 未知原拒绝渠道必须标为未知，不能把备用渠道误写成原来源。
- 成功结果区分“选中了备用”“已提交/等待任务完成”和“本轮已成功完成”，不能仅凭 HTTP 200 判断流式或异步任务最终成功。
- 成功转送使用现有日志表的系统类事件承载非错误路由结果，使用固定事件标识及管理员元数据；不新增消费记录、不伪造 `cyber_policy` 错误，不依赖消费日志开关才能查询。
- 失败继续复用现有失败日志并附加路由信息。Cyber 事件查询显式合并符合条件的系统类事件和原错误事件，保持分页/总数语义，不扫描全部成功消费记录来寻找转送。
- 普通使用日志的成功详情同步展示路由原因；路由敏感信息仍遵守管理员可见范围，普通用户只看到允许公开的错误原因。
- 写日志失败不重放上游请求；记录独立写入失败指标，不能因观测失败触发重复执行。
- 不额外记录密钥、认证令牌、原始请求正文或隐私上下文。会话内容继续走现有会话审计开关和加密策略，不因转送改变采集规则。

### 8.2 计费不变量

实施前必须完整阅读并遵守 `.agents/rules/billing.md`。

- 在确定最终渠道、实际分组、执行插件和兼容性检查完成后，再走原有价格估算和预扣费流程。
- 转送前的本地拒绝不新增上游消费；不新增处罚费用，也不改变既有违规费用规则。
- 不复用原渠道或原插件的价格快照去结算备用执行结果；不把原候选误记为一次已调用。
- 保留现有 BillingSession 的一次预扣、结算和最终失败退款规则；不因转送创建第二套收费流程。
- 流式中断、客户端取消和异步任务已提交后的处理，沿用实际执行链路的既有结算语义，不笼统承诺所有失败都免费或退款。
- 日志中的实际渠道、分组、执行插件、用量及费用归属必须一致；不得因新增路由事件重复统计消费。

### 阶段一：配置契约与路由约束

## 11. Review 修订记录与剩余影响

| Review 问题 | 本版修订 |
| --- | --- |
| 用高优先级强制渠道可能绕过普通渠道池约束 | 改为候选范围交集，硬绑定冲突明确失败 |
| 封禁到期立即恢复可能破坏有状态响应链 | 限定为可独立请求，已有连接不迁移；状态归属另案 |

| WebSocket 新连接支持被误解为全会话无感切换 | 拆分首轮与已连接处理，明确重连和上下文前提 |
