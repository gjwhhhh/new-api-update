# 渠道级定期健康检查开发计划

## 背景与目标

当前“定期渠道测试”只有系统级开关、测试模式和测试间隔。启用“定时全量测试”后，系统会在每个全局间隔内测试所有未被手动禁用的渠道；无法针对单个渠道设置不同的测试频率、排除渠道，或只对某个渠道执行被动恢复检查。

本计划将定期测试扩展为“全局默认 + 渠道级覆盖”。渠道的测试频率定义为“每隔 N 分钟测试一次”，不支持固定每日时刻或 Cron 表达式。

目标：

- 保留现有全局配置作为默认行为，已有渠道升级后不改变行为。
- 允许管理员为单个渠道设置独立测试间隔。
- 允许渠道不参与任何后台健康检查。
- 允许渠道只在自动禁用后进行被动恢复检查。
- 继续复用现有系统任务、跨实例租约和任务进度机制，避免为每个渠道创建独立定时器。

非目标：

- 不支持固定时刻、日期、时区或 Cron 调度。
- 不改变管理员手动测试单个渠道的功能。
- 一期不改变手动“测试全部渠道”的语义。

## 配置模型

在渠道的额外设置中增加健康检查配置。未配置时使用 `inherit`，完全继承系统级设置。

```json
{
  "health_check": {
    "mode": "inherit",
    "interval_minutes": null
  }
}
```

字段定义：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `mode` | string | `inherit`、`scheduled`、`passive_recovery` 或 `excluded` |
| `interval_minutes` | nullable integer | 大于等于 1；为空时使用系统级测试间隔 |

渠道模式的有效行为如下：

| 模式 | 定时全量任务中的行为 | 自动禁用后的行为 |
| --- | --- | --- |
| `inherit` | 跟随系统级测试模式 | 跟随系统级测试模式 |
| `scheduled` | 到期后参与测试 | 到期后参与测试，成功时允许恢复 |
| `passive_recovery` | 不参与全量测试 | 仅在渠道为自动禁用状态且到期后测试 |
| `excluded` | 始终跳过 | 始终跳过 |

`scheduled` 的语义与现有“定时全量测试”一致：手动禁用的渠道始终跳过，自动禁用渠道可被探测并在成功后恢复。`passive_recovery` 不会因探测失败再次执行自动禁用逻辑。

## 调度与状态设计

### 独立记录后台测试时间

新增渠道字段 `last_auto_test_time`（Unix 时间戳）记录一次后台测试完成的时间。不能复用现有 `test_time`，因为它同时会被管理员的手动单渠道测试更新；复用会使手动测试意外推迟定时测试。

渠道级配置存放在现有额外设置 JSON 中，运行状态存放在独立字段中：

- 配置更新不会与后台写入测试时间相互覆盖。
- 可直接在渠道列表或编辑页展示“上次自动测试时间”。
- 渠道被复制时重置该时间，避免新渠道继承旧渠道的测试历史。

### 有效间隔与任务唤醒

系统级“测试间隔”保留，语义调整为未覆盖渠道的默认间隔。系统任务的有效运行间隔为下列值的最小值：

- 全局默认间隔；
- 所有启用了渠道级定期测试或被动恢复的渠道的有效间隔。

每次任务执行时只选择“已到期”的渠道，而不是在最短间隔内重新测试所有渠道。例如，全局默认 60 分钟、渠道 A 为 10 分钟、渠道 B 继承全局时，任务每 10 分钟执行一次；渠道 A 每次均可能被选中，渠道 B 仅在距其上次自动测试满 60 分钟时被选中。

到期条件为：

```text
last_auto_test_time 为空
或 当前时间 - last_auto_test_time >= effective_interval_minutes
```

测试完成后更新 `last_auto_test_time`。任务取消或实例租约丢失时不将未完成渠道标记为已测试。管理员修改模式或间隔时，将该渠道的 `last_auto_test_time` 重置为 0，使新配置在下一次调度中生效。

## 后端改造范围

1. 扩展渠道额外设置 DTO，定义模式常量、配置结构、解析和校验逻辑。
2. 扩展 `Channel` 模型与跨数据库迁移，新增 `last_auto_test_time`；SQLite、MySQL 和 PostgreSQL 均需验证迁移与更新语句。
3. 改造定期渠道测试处理器：根据有效最短间隔创建系统任务。
4. 改造自动测试选渠逻辑：按渠道模式、状态和到期时间过滤渠道。
5. 在每个后台测试完成后原子更新渠道的响应时间、常规测试时间和后台测试时间；手动测试只维持现有的响应时间与常规测试时间更新。
6. 保持手动“测试全部渠道”使用原有全量语义，不应用渠道级 `excluded`/`passive_recovery` 过滤；单渠道手动测试也不受影响。
7. 将任务结果补充为已测试、跳过、恢复、禁用的数量，便于后台查看运行效果。

## 前端改造范围

### 配置入口与布局

入口放在“渠道管理 → 新建/编辑渠道”的编辑抽屉中。现有抽屉已经在“高级设置”内按导航分组展示“渠道额外设置”和“上游模型检测设置”；新增一个独立的“渠道健康检查”子区块，放在它们之后，而不是把配置暴露在原始 JSON 编辑器中。

独立区块的原因是该配置会改变后台任务行为，管理员需要看懂实际效果和风险，不能要求其记忆 JSON 字段。

区块包含以下内容：

1. **自动测试策略**：使用单选卡片或下拉选择，而非多个互相排斥的开关。
2. **渠道测试间隔（分钟）**：仅在“定时测试”和“仅被动恢复”时显示；可留空，留空即继承全局默认间隔；输入值必须为正整数。
3. **当前状态**：展示上次自动测试时间；当前选择的策略与渠道级间隔直接显示在表单中。
4. **全局开关提示**：若系统级“定期渠道测试”关闭，仍可保存渠道配置，但在区块顶部显示提示：“全局自动测试已关闭；保存的渠道策略将在全局开关重新启用后生效。”
5. **测试模型提示**：提示该健康检查沿用本渠道已有的“测试模型”配置，不在此处重复选择模型。

### 管理员配置流程

管理员编辑某个渠道时，按以下方式配置：

| 目标 | 在“自动测试策略”中选择 | 间隔输入 | 保存后的实际效果 |
| --- | --- | --- | --- |
| 与其他渠道一致 | `继承全局（默认）` | 不显示 | 使用系统级模式和系统级间隔 |
| 每 10 分钟主动测试一次 | `定时测试` | `10` | 该渠道到期即参加后台探测，即使系统全局为被动恢复模式 |
| 不参加全量测试，仅每 30 分钟尝试恢复 | `仅被动恢复` | `30` | 正常时不发送测试；被自动禁用后，每 30 分钟探测一次，成功则恢复 |
| 永远不进行后台测试 | `不参与自动测试` | 不显示 | 既不参加全量测试，也不参加自动恢复；管理员仍可手动测试 |

策略卡片应提供即时说明：

- **继承全局**：显示“使用系统级定时全量测试/被动恢复设置”。
- **定时测试**：显示“渠道在启用和自动禁用状态下均可被后台探测；手动禁用状态始终跳过”。
- **仅被动恢复**：显示“只有真实请求失败导致自动禁用后才会测试；失败不会再次触发自动禁用”。
- **不参与自动测试**：以警示样式说明“该渠道不能依靠后台测试自动恢复，请通过手动测试或手动启用处理”。

切换到 `inherit` 或 `excluded` 时，前端在提交数据中明确将 `interval_minutes` 写为 `null`，避免历史覆盖间隔在以后重新生效。切换策略或修改间隔时，后端会重置该渠道的后台测试时间，因此前端保存成功后提示“新策略将在下一次调度中生效”。

### 表单、接口与展示数据

渠道编辑表单新增两个仅用于表单编辑的字段：

```ts
health_check_mode: 'inherit' | 'scheduled' | 'passive_recovery' | 'excluded'
health_check_interval_minutes?: number
```

它们按现有“上游模型检测设置”的方式序列化到渠道额外设置 JSON：

```json
{
  "health_check": {
    "mode": "scheduled",
    "interval_minutes": 10
  }
}
```

前端改造点包括：

- 在 `ChannelFormValues`、Zod schema、默认值转换和提交转换中加入这两个字段。
- 编辑已有渠道时，将额外设置 JSON 解析为表单默认值；未包含 `health_check` 时默认 `inherit`。
- 提交时仅更新 `health_check` 这部分额外设置，不破坏已有的代理、模型更新检测和渠道类型专属配置。
- 渠道详情/列表接口返回只读的 `last_auto_test_time`。有效模式和间隔由渠道设置及当前全局设置共同决定，首期不展示依赖本机时钟推算的“下次测试时间”。
- 在渠道列表中增加可选的“健康检查”列或状态 Badge：`继承全局`、`每 N 分钟`、`被动恢复`、`已排除`。首期至少在编辑抽屉展示，列表列可作为默认隐藏列，避免表格过宽。

### 交互和校验细节

- 间隔输入使用 `type='number'`、`min=1`、`step=1`；Zod 和后端均校验为安全范围内的整数，前端校验不替代后端校验。
- 输入为空代表继承全局间隔，而不是 0 分钟或停止测试；`0`、负数、小数、非数字均展示字段级错误。
- 选择 `excluded` 时显示明确的警示说明：它只关闭后台健康检查，**不会**禁用渠道，也**不会**阻止手动测试；保存后才生效。
- 仅当当前操作者拥有渠道敏感写权限时允许编辑；无权限用户可查看只读状态，不显示可保存控件。
- 所有文本通过 `useTranslation()` 渲染，并补齐支持语言的翻译；状态颜色之外同时提供可读文字，保证键盘操作和无障碍访问。

### 与系统级设置的关系

系统设置页保持“定期渠道测试”开关、全局模式和全局间隔，但文案调整为：

- “全局默认测试模式”：只应用于选择“继承全局”的渠道。
- “全局默认测试间隔”：只应用于未设置单独间隔的渠道。
- “定期渠道测试”仍是总开关；关闭时任何渠道级策略都不创建后台测试请求。

所有新增用户可见文本使用 `react-i18next`，并补齐现有前端支持语言的翻译。

## 兼容性、权限与可观测性

- 未配置 `health_check` 的历史渠道按 `inherit` 处理，确保发布后与现有全量/被动恢复行为一致。
- 该配置归入渠道敏感设置，沿用现有渠道敏感写权限和审计记录。
- 管理员手动测试始终可用于排障；“不参与自动测试”不等于禁用渠道，也不会禁止手动测试。
- 运行日志记录渠道 ID、有效模式、有效间隔、是否因未到期或策略被跳过，避免排障时无法解释测试结果。

## 验证计划

### 后端单元测试

- 历史空配置正确继承全局全量模式和全局被动恢复模式。
- 四种渠道模式在启用、自动禁用、手动禁用状态下的选渠结果正确。
- 不同渠道间隔混跑时，仅到期渠道被选中。
- 手动测试不会更新 `last_auto_test_time`，也不会被 `excluded` 策略阻止。
- 配置变更后渠道在下一轮成为到期状态。
- 后台测试成功/失败、自动禁用/恢复、取消任务时的时间戳更新正确。
- 系统任务按最短有效间隔运行，且仍受现有跨实例任务锁保护。

### 数据库与接口测试

- SQLite、MySQL、PostgreSQL 的新增字段迁移、读写与克隆重置验证。
- 渠道创建和更新接口的配置校验：非法模式、非整数、0、负数和超范围值均应拒绝。
- 权限测试确认普通渠道读取权限不能修改健康检查配置。

### 前端验证

- 表单默认值、保存/回显、清空间隔后继承全局、各模式条件展示。
- i18n 同步与生产构建。

## 发布顺序

1. 先发布后端的数据结构、迁移和兼容读取，历史渠道继续走全局行为。
2. 发布前端渠道级配置入口。
3. 在测试环境验证 10/30/60 分钟的混合间隔、自动禁用恢复和多节点部署。
4. 生产发布后观察任务执行量、单轮耗时和渠道恢复日志；必要时调整允许的最小间隔与并发策略。
